WINDOWS MEMORY FORENSICS — PART 04

Userland API hooking: IAT hooks, trampolines, and how apihooks finds them

Previous parts covered process enumeration, DLL analysis, and how the Windows loader brings a process to life. This part focuses on a technique attackers use to intercept execution after a process is already running: API Hooking.

Series — Windows Memory Forensics, Part 04 Topic — IAT Hooking, Inline/Trampoline Hooking, apihooks Read — ~15 min

01Why userland hooks?

As kernel-level protections like PatchGuard made traditional kernel hooks (SSDT/IDT patching) increasingly impractical, attackers shifted their focus to Userland Hooking.

Userland hooks operate at the application level, which means:

  • They don't affect the entire system — only specific processes
  • They are easier to implement than kernel hooks
  • Legitimate software also uses them heavily, creating more false positives for investigators

02IAT hooking

2.1 Background: what is the IAT?

When you write a program and want to use a ready-made function like CreateFile or MessageBox, those functions don't live in your code — they live in system DLLs like kernel32.dll and user32.dll. The problem: the address of any given function in memory isn't fixed. It changes between Windows versions and updates, so you can't hardcode it.

The solution is the Import Address Table (IAT) — a structure inside every PE file (.exe or .dll) that acts like a shopping list. It contains the names of the external functions the program needs and, after the loader runs, the actual in-memory addresses of those functions.

2.2 How IAT hooking works

IAT Hooking modifies an entry inside a process's Import Address Table, replacing the legitimate function address with the address of malicious code:

Program
   ↓
IAT Entry  ← address replaced by attacker
   ↓
Malicious Function

Every time the program calls that function, it silently gets redirected to the attacker's code instead.

2.3 Detectability

IAT Hooking is relatively simple to implement — and relatively simple to detect, by inspecting the IAT and comparing its entries against the expected export addresses of the loaded DLLs.

03Inline / trampoline hooking

3.1 How it works

Instead of modifying the IAT, the attacker goes directly into the function's code in memory and overwrites the first 5 bytes with a JMP instruction pointing to malicious code:

Original Function
      ↓
   JMP malicious code    ← first 5 bytes overwritten
      ↓
Attacker Memory
      ↓
(malicious code executes, then jumps back to original function)

After the malicious code runs, execution jumps back to the rest of the original function so the program continues normally and nothing looks broken.

3.2 Why it's more dangerous

The modification exists only in memory — the DLL file on disk remains completely untouched. Security tools that only inspect files on disk will never see it. Only memory analysis can reliably surface it.

The plugin produces large amounts of output — there are many functions and memory locations to inspect. The goal is to look for anomalies, not to assume every hook is malicious.

To scope output to a specific process:

apihooks -p <PID>

Use -R to skip kernel-mode checks.

05How apihooks works internally

Step 1: determine the expected address

For every process, the tool knows which DLLs are loaded and where each one is mapped in memory. For example, if kernel32.dll is loaded at base address 0x7c800000, and the export table inside that DLL says CreateFile is at offset 0x1234, then:

Expected address of CreateFile = 0x7c800000 + 0x1234 = 0x7c801234

This expected address is derived from the Export Table of each loaded DLL — a structure inside the DLL that maps function names to their offsets.

Step 2: read the actual address from the IAT

The tool opens the process's IAT and reads the address currently written next to the function name CreateFile.

Step 3: compare the two

  • If the IAT address matches the expected export address → no hook, everything is clean
  • If the IAT address differs from the expected export address → hook detected; the tool takes the new address and begins inspecting it

Step 4: identify the destination (Mapped vs Private)

The tool takes the new (hooked) address and queries the memory from the VAD (Virtual Address Descriptor): "What region does this address belong to, and where did it come from?"

The VAD entry contains:

  • Start address of the region
  • Size of the region
  • Permissions (Read/Write/Execute)
  • Source type: is it Mapped (backed by a file on disk) or Private (allocated in memory with no file backing)?

Two outcomes:

If the region is Mapped: the tool retrieves the associated file name from the VAD and reports something like: "This hook jumps to an address inside C:\Windows\System32\kernel32.dll." This is not automatically malicious — it may be legitimate security software or a known-good hook (needs further investigation).

If the region is Private: the region was allocated in memory (via VirtualAlloc) and has no backing file on disk. The tool cannot find a file name, so it reports the Hooking Module column as "Unknown" — and that is a strong indicator of injected, fileless code.

06Legitimate API hooks

Hook does not equal malware. Many legitimate applications use API hooking extensively. Examples:

  • svchost
  • VMware Tools
  • Security software (AV/EDR)
  • CodeMeter/HASP license protection

Known legitimate Microsoft DLLs that frequently appear as hooking modules and should be treated as potentially known-good:

setupapi.dll
mswsock.dll
sfc_os.dll
adsldpc.dll

07Case study — Zeus / Zbot

Zeus used extensive Userland DLL Hooking across infected systems.

Example hook found in memory

Process:     services.exe
Victim DLL:  USER32.dll
Function:    GetClipboardData
Hook Type:   Inline/Trampoline

The original function's first bytes had been replaced with:

JMP 0x7f4fd5

The destination address:

<unknown>

The jump target was memory that wasn't mapped to any normal file-backed module — meaning the code being jumped to existed only in private, allocated memory with no corresponding file on disk.

Zeus had nearly 400 DLL hooks across a single process — which by itself is a strong statistical anomaly, entirely apart from what each individual hook was doing.

08What makes an API hook suspicious?

Look for combinations of the following signals:

  1. Large number of hooks — hundreds of hooks in a single process is abnormal
  2. Hooking security-sensitive functions — clipboard access, cryptographic APIs, network calls, authentication functions
  3. Hooking Module = <unknown> — the hook destination is in private, fileless memory
  4. Jump destination in unmapped or anonymous memory — not associated with any DLL on disk
  5. Hooks inside unexpected processes — e.g. clipboard hooks inside services.exe
  6. Functions that make no sense for the process — a system service hooking GetClipboardData has no legitimate reason to do so
Example suspicious pattern: 
services.exe
   ↓
GetClipboardData()
   ↓
JMP
   ↓
<unknown memory>
That combination is significantly more suspicious than a single hook from a known security DLL.

09Trampoline hooking — deep dive

9.1 The core problem

The term "Inline Hook" describes placing a JMP at the start of a function. But that immediately creates a problem: what happens to the original bytes that got overwritten?

Assume we have a function in memory:

MyFunction:

0x1000:  push rbp
0x1001:  mov  rbp, rsp
0x1004:  sub  rsp, 20h
0x1008:  mov  eax, 1
0x100D:  ...

We want to intercept it:

MyFunction()
      ↓
   Hook()
      ↓
Original MyFunction()

The easiest approach: overwrite the first bytes at 0x1000 with a JMP to our hook:

0x1000: jmp Hook

But now we have destroyed the original instructions:

push rbp
mov  rbp, rsp
sub  rsp, 20h

When the hook finishes and tries to call the original function, it can't jump back to 0x1000 — that address now contains jmp Hook, which creates an infinite loop:

Hook → 0x1000 → Hook → 0x1000 → ...

This is exactly why the Trampoline exists.

9.2 What is a trampoline?

A trampoline is a copy of the overwritten original instructions, followed by a jump back into the original function at the point past the overwritten region.

We copy the bytes we destroyed into a new location in memory:

Trampoline @ 0x8000:

0x8000: push rbp
0x8001: mov  rbp, rsp
0x8004: sub  rsp, 20h
0x8008: jmp  0x1008      ← resume original function here

The jmp 0x1008 at the end returns execution to the first instruction in MyFunction that was not overwritten.

9.3 The complete picture

After hooking, memory looks roughly like this:

Full execution path:

Application
     |
     | CALL MyFunction
     v
+----------------+
| MyFunction     |
| JMP Hook       |
+-------+--------+
        |
        v
+----------------+
| Hook Function  |
+-------+--------+
        |
        | CALL Trampoline
        v
+----------------+
| Trampoline     |
| original bytes |
+-------+--------+
        |
        | JMP 0x1008
        v
+----------------+
| MyFunction     |
| remaining code |
+----------------+

9.4 Why not just copy the first 5 bytes?

x86/x64 instructions are variable length — they are not all the same size. For example:

push rbp       → 1 byte
mov  rbp, rsp  → 3 bytes
sub  rsp, 20h  → 4 bytes

If you blindly copy 5 bytes, you may cut an instruction in half:

Instruction A = 3 bytes
Instruction B = 4 bytes

Taking 5 bytes:
AAA BB  ← only 2 bytes of B — invalid machine code

A correct hooking implementation must perform instruction disassembly and copy complete instructions until it has covered at least the number of bytes it needs for the JMP. For example: 1 + 3 + 4 = 8 bytes, so all three instructions get copied.

9.5 Hook vs trampoline — they are not the same thing

A common point of confusion:

Purpose
HookThe interception logic — the code that receives execution and inspects/modifies behavior
TrampolineThe gateway that re-executes the overwritten original bytes and then returns to the rest of the original function

The hook calls the trampoline via a function pointer:

HookFunction(...)
{
    // inspect arguments, log, modify...

    return OriginalFunction(...);   // OriginalFunction points to the trampoline, not 0x1000
}

OriginalFunction here resolves to 0x8000 (the trampoline), not the real function's start address.

9.6 RIP-relative instructions (x64 problem)

On x64, many instructions use RIP-relative addressing:

mov rax, [rip + 0x1234]

The effective address depends on the current value of RIP. If this instruction originally lived at 0x1000 and you copy it to 0x8000, the same bytes now calculate a completely different effective address:

Original:   0x1000 + offset → 0x5000   (correct)
Trampoline: 0x8000 + offset → 0x9000   (wrong)

A correct trampoline implementation must detect these instructions and apply relocation/fix-ups when copying, rather than doing a blind memcpy. This is one of the primary reasons x64 hooking is significantly more complex than x86.

9.7 Relative CALL/JMP instructions

The same problem applies to relative CALL and JMP instructions:

call 0x12345678
jmp  0x12345678

If the displacement is relative to the instruction's address, copying it to a new location changes the target. A correct trampoline implementation must detect and handle:

  • RIP-relative references
  • Relative CALL instructions
  • Relative JMP instructions
  • Conditional branches

9.8 The long jump problem on x64

On x86, a JMP rel32 can reach anywhere within a ±2GB range relative to the instruction. On x64, if the hook lives far enough away in the address space that a rel32 can't reach it, a larger sequence is needed:

mov rax, HookAddress
jmp rax

This sequence is longer than a simple 5-byte JMP, which means more original instructions need to be copied into the trampoline to make room for it, increasing the complexity of the copy-and-fixup step.

9.9 Complete conceptual example

Before hooking:

Function @ 0x1000:

1000: push rbp
1001: mov  rbp, rsp
1004: sub  rsp, 20h
1008: mov  eax, 1
100D: pop  rbp
100E: ret

We decide the hook requires 8 bytes. We copy the first 8 bytes to the trampoline:

Trampoline @ 0x8000:

8000: push rbp
8001: mov  rbp, rsp
8004: sub  rsp, 20h
8008: jmp  0x1008

We overwrite the original:

Function @ 0x1000:

1000: jmp 0x5000     ← redirected to hook
1005: (padding)
1008: mov eax, 1
100D: pop rbp
100E: ret

Full execution flow:

CALL 0x1000
    ↓
JMP 0x5000          (hook)
    ↓
inspect / log
    ↓
CALL 0x8000         (trampoline)
    ↓
PUSH RBP
MOV  RBP, RSP
SUB  RSP, 20h
    ↓
JMP 0x1008          (resume original)
    ↓
MOV EAX, 1
POP RBP
RET

The Trampoline is not the Hook.
The Hook receives execution and applies its interception logic. The Trampoline preserves the original instructions that were overwritten and returns execution to the original function past the overwritten region.
