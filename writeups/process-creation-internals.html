WINDOWS MEMORY FORENSICS — PART 03

Process creation internals: from double-click to first instruction

Parts 01 and 02 covered how to find processes and validate what's loaded inside them. This part goes one level deeper: how a process actually comes into existence in the first place — from the double-click to the first executed instruction.

Series — Windows Memory Forensics, Part 03 Topic — EPROCESS, PE Header, PEB, VAD Tree, Paging Read — ~11 min

Understanding the creation flow in detail is what makes the forensic artifacts in Parts 01 and 02 make sense: why EPROCESS looks the way it does, why the PEB exists at all, and how the PE loading process, the VAD Tree, and memory paging all fit together.

01What happens when you double-click notepad.exe

Step 1: Request execution (user mode)

You double-click the file. The shell (e.g. explorer.exe) calls a function named CreateProcess.

Step 2: Create the EPROCESS (kernel mode)

The request drops into the kernel, which builds a data structure in its own memory called EPROCESS.

Purpose: this is the process's official record — it holds the Process ID (PID), the security structure (Access Token), and which process is the parent.

Step 3: Allocate the virtual address space

Windows builds a virtual address space for the process (e.g. 4GB on a 32-bit system, or a vastly larger space on 64-bit).

Purpose: give the process an empty address space, completely independent from every other process — without reserving any physical RAM yet.

Step 4: Read the PE header and map the sections

Windows opens the .exe file on disk and reads its structure (the PE Header).

Step 5: Resolve imports

Windows inspects the Imports section and loads the required DLLs (e.g. kernel32.dll), writing the real function addresses into a table called the IAT (Import Address Table).

Step 6: Create the primary thread and start execution

Windows creates an ETHREAD and sets up the CPU to begin executing code at the address written in AddressOfEntryPoint.

02What is EPROCESS, exactly?

EPROCESS is a kernel data structure in Windows representing a process from the kernel's point of view.

So when Windows creates a process such as:

notepad.exe
PID = 4200

the kernel holds an object/structure roughly called:

EPROCESS

representing that process and holding the information Windows needs to manage it.

2.4 Which field connects them?

In modern Windows, EPROCESS contains a field called:

ActiveProcessLinks

of type:

LIST_ENTRY

and LIST_ENTRY itself is:

typedef struct _LIST_ENTRY {
    struct _LIST_ENTRY *Flink;
    struct _LIST_ENTRY *Blink;
} LIST_ENTRY;

So conceptually:

│
└── ActiveProcessLinks
       ├── Flink
       └── Blink

ActiveProcessLinks is exactly what places an EPROCESS into the Active Process List.

03What is the PE header?

Think of the PE Header as the program's "ID card" or "specification sheet." The moment you double-click an .exe, the OS reads this card to understand the file's dimensions, where to place it in RAM, and how to run it.

3.1 The DOS header

The first data structure encountered at the very start of any Windows executable (.exe or .dll).

  • Fixed size: 64 bytes (0x40)
  • Located at offset 0x00
  • Contains many legacy fields (used by old MS-DOS systems), but modern Windows only cares about two of them

1. The Magic Signature: e_magic

  • Location: the very start of the file, offset 0x00
  • Value: always 0x5A4D in hex, equal to the characters MZ (named after programmer Mark Zbikowski, who designed the format)
  • Purpose: Windows reads these two characters to confirm the file is actually a valid Windows executable; without MZ, the system refuses to run it

2. The Golden Pointer: e_lfanew

  • Location: at the end of the DOS Header, offset 0x3C
  • Purpose: holds a number (address/offset) pointing directly to the start of the real PE Header (the NT Headers) inside the file
  • Why it matters: without this pointer, Windows wouldn't know exactly where the PE Header begins, since the space between the DOS Header and the PE Header can vary in size from file to file

3.2 The NT headers (the beating heart)

The most important structure, containing 3 parts:

  • Signature — the PE-specific signature, the characters PE\0\0
  • File Header — basic information about the file itself: processor architecture (32-bit or 64-bit?), number of sections inside the file, file creation date/time
  • Optional Header — despite the name "optional," it's mandatory in .exe files:
    • AddressOfEntryPoint — the address where the processor begins executing code
    • ImageBase — the preferred address where the file wants to be loaded in memory
    • SizeOfImage — the total size the file occupies once unfolded in memory

3.3 The section table

Works like a conversion map that tells Windows how to take the data written in the file on disk and place it correctly in memory (RAM). Think of the Section Table as containing a "data form" for each section (like .text or .data), with 4 key parameters:

ParameterTechnical NameSimple Function
Location on diskPointerToRawDataWhere the section starts inside the .exe file on disk
Size on diskSizeOfRawDataThe real size of the section's data on disk
Location in memoryVirtualAddress (RVA)The address the section will land at in memory (relative to the program's base address)
Size in memoryVirtualSizeThe size the section will occupy in virtual memory

3.4 How Windows maps a section like .text into memory

Let's apply the formula to a practical example:

  1. Program base address (ImageBase): suppose Windows decides to load the program at address 0x400000 in memory
  2. Reading section data from the table: Windows looks at the Section Table row for .text and finds VirtualAddress = 0x1000 and PointerToRawData = 0x400
  3. The mapping process: Windows goes to the disk at location 0x400 and reads the instruction code, then calculates its final location in memory with a simple addition — as a result, Windows moves the code and places it at address 0x401000 in memory

3.5 Security permissions (characteristics)

The Section Table doesn't just define addresses — it also gives each section specific access permissions:

  • .text section: gets Execute/Read permission (execute and read only), so the processor can execute the code, and no program can modify it
  • .data section: gets Read/Write permission, used to store variables

3.6 The five loading stages

1. Headers Parsing — the OS opens the file and reads the main parts in order: DOS Header → PE Header → Optional Header. Goal: confirm the file is valid and intended for Windows, and learn the basic instructions for its size and location.

2. Sections Table Parsing — the system reads the Section Table to verify its validity and boundaries. Goal: identify the sections present (like .text and .data) and how much space and what permissions each needs.

3. Mapping — Windows builds the virtual address space and starts moving each section from disk into its appropriate address in memory, based on ImageBase and VirtualAddress. Goal: unfold the file's parts inside RAM in an organized way.

4. Imports Resolution — Windows looks at the Imports section (e.g. kernel32.dll or user32.dll), loads these libraries into memory, and writes the real function addresses into a table called the IAT (Import Address Table). Goal: connect the program to the helper functions it needs from the system.

5. Execution — the CPU jumps directly to the address written in AddressOfEntryPoint and executes the first instruction there. Result: the program starts running and its window appears.

04The PEB (Process Environment Block)

PEB stands for Process Environment Block — a data structure representing a process's information in User Mode. Windows creates this structure for every running process so it can hold that process's runtime information without constantly having to go back into Kernel Mode.

4.1 Key elements of the PEB structure

1. BeingDebugged — a one-byte field. Its value is 1 if the process is being traced by a debugger, and 0 if running normally. Attackers and malware check this field to apply Anti-Debugging techniques.

2. Ldr — PEB_LDR_DATA — a pointer to a structure containing a list of all modules and external DLLs loaded into the process. This list is a doubly linked list showing DLL addresses and their location in memory.

3. ProcessParameters — RTL_USER_PROCESS_PARAMETERS — a structure holding the process's startup parameters, such as executable file path, command line, current directory, and environment variables.

4. ProcessHeap — a pointer to the process's main heap, used for dynamic memory allocation.

5. ImageBaseAddress — a pointer to the address where the main .exe file is loaded within the process's virtual memory.

4.2 _EPROCESS is not a direct "container" of the PEB

The _EPROCESS object in the kernel does not contain the full PEB structure inside it — it only contains a pointer to the PEB's address in User Space:

  • In Kernel Space: the _EPROCESS structure contains a field called Peb, of type pointer (struct _PEB*)
  • In User Space: the actual memory where the PEB structure is built

05The VAD tree (Virtual Address Descriptor tree) — in depth

The VAD Tree is the fundamental data structure the kernel in Windows uses to track and count every memory region reserved inside a process's Virtual Address Space.

Imagine the process's Virtual Address Space is a huge piece of land. When the process wants to reserve a plot (carve out memory for Code, Stack, or Heap), the OS builds a land registry recording where the plot starts and ends, address-wise, and what permissions it has (Read-Only, Write, or Execute). That land registry, at the kernel level, is the VAD Tree.

5.1 Key data stored in each tree node

Each node inside the VAD tree represents a reserved memory region and contains:

1. Addresses (Starting & Ending VPN) — defines the start and end virtual memory address of the region reserved.

2. Allocation Type — indicates whether the space is Private Memory (memory private to this process only, like the Heap and Stack) or a Mapped File / Section (memory tied to a file on disk, like an .exe file or DLL files).

3. Protection Flags — define what's permitted on this region, such as PAGE_READONLY, PAGE_READWRITE, or PAGE_EXECUTE_READWRITE (a very dangerous permission, because it allows writing and executing code in the same region at the same time).

06What is a page, simply put?

Windows and the CPU don't treat RAM as a random sea of bytes, and they don't reserve memory byte-by-byte. Instead, they divide both virtual and physical memory into small, fixed-size blocks.

  • The standard size of a single Page on most systems is 4 Kilobytes (4096 bytes)
  • The Page is the smallest building-block unit the CPU and OS can reserve, move, or apply security permissions to (Read, Write, Execute)

6.1 Analogy: being inside the RAM giant

Imagine RAM as a giant notebook:

The Page (a page in the notebook): one sheet of the notebook (fixed size, 4KB). You can't tear off half a sheet and write on it — you either use the whole sheet or leave it empty.

The PTE (Page Table Entry): the index tag glued to the top of that sheet. This tag says: "Where is this sheet actually located in real RAM? And is it allowed to be written to, or read-only?"

6.2 The complete architecture with the VAD tree

To tie the whole picture together so it never gets confusing again:

  1. The VAD Node (tree node): represents a large space (e.g. a program requests 1 Megabyte). That space contains 256 pages.
  2. The Pages: that 1 Megabyte gets split into 256 small chunks, each 4KB.
  3. The PTE table (the tags): contains 256 entries (PTEs), each entry holding one page and responsible for translating its address and monitoring its current permissions in front of the CPU.

07Memory management mechanics

Imagine you want to reserve a table at a big restaurant:

7.1 Step one: initial reservation (MEM_RESERVE)

What happens? You call the restaurant and say: "I want to reserve a table for 10 people at 8." What does the restaurant do? It puts your name in the book: "Table 5 is reserved for so-and-so."

In memory: Windows records in the VAD Tree that this address range (e.g. from 0x1000 to 0x5000) is reserved for your program. The reality: no food is put on the table, and no space was actually pulled from real RAM — just "a name on paper."

7.2 Step two: commitment (MEM_COMMITTED)

What happens? You confirm with the restaurant and say: "Prepare the order and the cost, we're on our way." What does the restaurant do? It ensures it has enough food in the kitchen for 10 people, but hasn't plated the food yet!

In memory: Windows checks RAM and the Page File and guarantees there's enough free space for this page if you decide to use it, and sets the permissions (like Read/Write). The reality: real RAM still hasn't had anything placed into it!

7.3 Step three: actual access (page fault, then demand paging)

What happens? The moment the guest sits down and reaches out to eat (i.e., the program tries to read or write to memory for the first time):

  • The CPU: checks the PTE table and finds the page empty, with no code actually backed by real RAM!
  • Reaction: the CPU raises an alarm called a Page Fault.
  • The Kernel steps in: the kernel hears the alarm, goes and opens RAM, grabs a real free physical frame, links it to that address, and updates the PTE to make it valid (Valid = 1).
  • From this moment on: the data is actually inside RAM and you can use it directly!

08Why this matters for the investigation

Everything explained in this part maps directly onto the forensic artifacts covered in Parts 01 and 02:

  • The EPROCESS/ActiveProcessLinks walk is exactly what pslist traverses, and exactly what DKOM manipulates
  • The PEB's ImageBaseAddress field is exactly the value ldrmodules compares against the VAD
  • The VAD Tree's Protection and Type fields are exactly what malfind and ldrmodules inspect to flag suspicious memory regions
